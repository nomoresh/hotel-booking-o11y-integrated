# 시장·서비스 비교 분석 및 클라우드 네이티브 차별화 도출

## 1. 비교 분석 개요

본 비교 분석은 호텔·숙박 예약 서비스를 클라우드 네이티브 관점에서 비교하고, 실제 운영 과정에서 발생할 수 있는 문제를 도출하기 위해 수행하였다.

비교 대상은 해외 서비스인 **Airbnb, Agoda**와 국내 서비스인 **야놀자, 여기어때**로 선정하였다. 주요 비교 항목은 다음과 같다.

- 시스템 아키텍처 및 MSA 적용 여부
- Kubernetes 및 컨테이너 활용
- CI/CD와 배포 전략
- 메트릭·로그·분산 추적 구성
- 서비스 메시 적용 여부
- 운영상 강점과 한계

> 각 기업의 내부 시스템 전체가 공개된 것은 아니므로, 공개 기술 블로그와 발표 자료에서 확인되지 않은 부분은 `추정` 또는 `확인 불가`로 표기하였다.

---

## 2. 비교 대상 서비스 선정

| 구분 | 서비스 | 선정 근거 |
|---|---|---|
| 해외 | Airbnb | 글로벌 숙박 예약 플랫폼으로 Kubernetes, Istio, Observability 등 대규모 운영 사례를 공개하고 있음 |
| 해외 | Agoda | 호텔 예약 중심의 글로벌 서비스로 MSA, Kubernetes CI/CD, OpenTelemetry 활용 사례를 공개하고 있음 |
| 국내 | 야놀자 | 국내 대표 숙박·여행 플랫폼으로 검색, 예약, 결제, 프로모션 등의 복합 서비스 흐름을 비교하기 적합함 |
| 국내 | 여기어때 | EKS, Argo CD, Helm, GitLab CI 등 클라우드 네이티브 운영 사례를 공개하고 있음 |

Airbnb와 Agoda는 글로벌 규모의 트래픽과 다수의 마이크로서비스를 운영한다는 점에서 대규모 시스템 운영 사례를 분석하기 적합하다.

야놀자와 여기어때는 국내 숙박 예약 서비스의 사용자 패턴과 특가·프로모션 트래픽을 분석하기 적합하며, 특히 여기어때는 EKS와 GitOps 관련 기술 자료가 공개되어 있어 본 프로젝트와 직접적인 비교가 가능하다.

## 3. 클라우드 네이티브 비교 분석

### 3.1 전체 비교표

| 구분 | Airbnb | Agoda | 야놀자 | 여기어때 |
|---|---|---|---|---|
| 아키텍처 | Kubernetes 기반 대규모 분산 구조 | MSA 및 비동기 예약 처리 구조 | 대규모 분산 서비스 구조로 추정 | EKS 기반 컨테이너 배포 구조 |
| MSA | 적용 | 적용 | 적용 추정 | 부분적으로 공개 자료 확인 |
| CI/CD | 자체 배포 자동화 플랫폼 | GitLab CI/CD, Kubernetes Runner | 상세 구성 확인 제한 | GitLab CI, Argo CD, Helm |
| 배포 전략 | 점진적 Rollout 및 장애 격리 | 컨테이너 기반 자동 배포 | 상세 구성 확인 제한 | GitOps 기반 자동 배포 |
| 메트릭 | Prometheus 및 자체 메트릭 플랫폼 | 서비스·인프라 메트릭 수집 | 상세 구성 확인 제한 | Prometheus |
| 로그 | 자체 Observability 플랫폼 연계 | 로그와 고객 이슈 연계 | 상세 구성 확인 제한 | 구체적인 로그 스택 확인 제한 |
| 분산 추적 | OpenTelemetry 기반 구조 활용 | OpenTelemetry 적용 | 상세 구성 확인 제한 | 공개 자료에서 확인 제한 |
| 서비스 메시 | Istio 적용 | 적용 정황 확인 | 확인 불가 | 확인 불가 |

---

### 3.2 아키텍처 및 MSA

### **Airbnb**

Airbnb는 다수의 Kubernetes 클러스터와 워크로드를 운영하며, 일부 데이터 계층을 여러 클러스터와 가용 영역에 분산하여 장애 범위를 분리하고 있다.

서비스 수와 트래픽 규모가 크기 때문에 배포 자동화, 서비스 간 통신 제어, 모니터링 데이터 처리까지 별도의 플랫폼 수준으로 관리한다.

### **Agoda**

Agoda는 기능별로 독립적인 마이크로서비스를 운영하고 있으며, 예약 처리 과정에 비동기 메시지와 Agent 기반 구조를 활용한다.

예약 단계를 개별 서비스로 분리하면 서비스별 확장과 배포가 가능하지만, 서비스 간 의존성이 증가하고 비동기 처리 실패에 대한 추적과 보상 로직이 복잡해질 수 있다.

### **야놀자**

야놀자는 국내 대규모 숙박·여행 플랫폼으로 다수의 기능을 분리한 서비스 구조를 사용할 것으로 추정된다.

다만 이번 조사에서 내부 아키텍처, 서비스 간 통신 방식, Observability 구성에 대한 구체적인 공개 자료는 충분히 확보하지 못했으므로 세부 기술 사용 여부는 단정하지 않았다.

### **여기어때**

여기어때는 EKS 기반 Kubernetes 환경에서 애플리케이션을 운영하고, 공통 Helm Chart와 서비스별 `values.yaml`을 통해 배포 구성을 표준화한 사례를 공개하였다.

공통 Chart를 사용하면 서비스별 중복 설정을 줄일 수 있지만, 공통 Chart 변경이 여러 서비스에 영향을 줄 수 있으므로 변경 전 검증이 중요하다.

---

### 3.3 CI/CD 및 배포 전략

| 서비스 | 주요 구성 | 특징 |
|---|---|---|
| **Airbnb** | 내부 자동화 플랫폼, Kubernetes Rollout | 대규모 환경에 맞는 점진적 배포와 장애 격리 |
| **Agoda** | GitLab CI/CD, Kubernetes Runner | 빌드 환경 격리와 동적 확장 가능 |
| **야놀자** | 세부 공개 자료 제한 | 실제 배포 구조를 단정하기 어려움 |
| **여기어때** | GitLab CI, Argo CD, Helm | GitOps 기반 배포와 공통 설정 관리 |

Airbnb는 모든 워크로드를 동시에 변경하지 않고 단계적으로 배포하여 변경 위험을 줄인다. 다만 자체 배포 플랫폼을 운영하기 위한 높은 기술 역량과 운영 비용이 필요하다.

Agoda는 기존 VM 기반 CI Runner를 Kubernetes로 이전하여 빌드 환경을 격리하고 자원 활용도를 개선하였다. 그러나 Kubernetes와 Private Cloud 자체를 관리해야 하는 운영 부담이 존재한다.

여기어때는 GitLab CI에서 배포 파일과 이미지를 관리하고, Argo CD가 Git 저장소의 선언 상태를 Kubernetes에 반영하는 GitOps 방식을 활용한다. 이는 수동 배포로 발생하는 환경 불일치와 배포 이력 관리 문제를 줄이는 데 효과적이다.

---

### 3.4 Observability 비교

| 서비스 | Observability 특징 |
|---|---|
| **Airbnb** | 대규모 메트릭 처리를 위한 별도 모니터링 구조와 장애 격리 적용 |
| **Agoda** | OpenTelemetry를 활용해 로그·메트릭·트레이스를 고객 이슈와 연계 |
| **야놀자** | 공개 자료만으로 세부 구성을 확인하기 어려움 |
| **여기어때** | EKS 내부에서 Prometheus와 Alertmanager를 운영한 사례 확인 |

Airbnb는 Observability 데이터 자체가 대규모 트래픽이 될 수 있기 때문에 비즈니스 트래픽과 모니터링 트래픽을 분리하고, 모니터링 시스템 장애가 실제 서비스에 영향을 주지 않도록 구성하였다.

Agoda는 OpenTelemetry 기반 분산 추적을 적용하여 특정 고객 요청이 여러 서비스를 통과하는 과정을 확인할 수 있도록 구성하였다. 이를 통해 로그만으로 파악하기 어려운 서비스 간 지연이나 오류 발생 위치를 추적할 수 있다.

여기어때는 Prometheus와 Alertmanager를 통해 Kubernetes 및 애플리케이션 상태를 수집하고, 장애 상황에 대한 알림을 제공하는 구조를 운영한 사례가 공개되어 있다.

---

### 3.5 서비스 메시 비교

Airbnb는 Istio를 적용하여 Kubernetes와 VM 워크로드의 서비스 간 통신을 제어하고 있다. 서비스 메시를 사용하면 트래픽 제어, 암호화, 재시도, 관찰성 기능을 애플리케이션 코드와 분리할 수 있다.

Agoda는 Private Cloud 환경에서 서비스 메시를 통한 기본 가시성 제공 사례를 공개했지만, 구체적인 제품명과 전체 적용 범위는 확인되지 않았다.

야놀자와 여기어때는 공개된 자료만으로 서비스 메시 사용 여부를 명확히 확인하기 어려웠다.

서비스 메시를 적용하면 서비스 간 통신 관리가 편리해지지만, Sidecar 자원 사용량과 네트워크 구조 복잡도가 증가할 수 있으므로 서비스 규모에 따라 적용 여부를 결정해야 한다.

## 4. 서비스별 강점과 한계

### 4.1 Airbnb

#### 강점

- 대규모 Kubernetes 클러스터 운영 경험
- Istio 기반 서비스 간 트래픽 제어
- 점진적 배포를 통한 변경 위험 감소
- 대규모 Observability 데이터 처리 및 장애 격리
- 여러 클러스터와 가용 영역을 활용한 고가용성 구성

#### 한계

- 자체 플랫폼과 서비스 메시 운영 복잡도가 높음
- 운영에 전문 인력과 높은 비용이 필요함
- 워크로드와 클러스터가 증가할수록 버전 및 정책 관리가 어려움
- 중소 규모 프로젝트가 동일한 구조를 적용하기에는 부담이 큼

### 4.2 Agoda

#### 강점

- 기능별 마이크로서비스의 독립적인 개발과 배포
- 비동기 메시지 기반의 유연한 예약 처리
- Kubernetes Runner를 통한 CI 실행 환경 격리
- OpenTelemetry 기반 분산 추적
- 트래픽에 따른 서비스별 확장 가능

#### 한계

- 서비스 간 의존성이 증가하면 장애 영향 분석이 어려움
- 비동기 처리 실패와 중복 메시지에 대한 대응이 필요함
- Private Cloud와 Kubernetes 플랫폼 운영 부담이 존재함
- 테스트 환경에서 여러 의존 서비스를 구성하기 어려움

### 4.3 야놀자

#### 강점

- 국내 숙박·여행 도메인을 대표하는 서비스
- 검색, 예약, 결제, 프로모션 등 다양한 업무 흐름 보유
- 국내 특가 및 성수기 트래픽 분석에 적합함

#### 한계

- 내부 아키텍처와 배포 구조에 대한 공개 자료가 제한적임
- Observability 및 서비스 메시 적용 여부를 구체적으로 확인하기 어려움
- 공개 자료만으로 기술적 강점과 한계를 상세히 비교하는 데 제한이 있음

### 4.4 여기어때

#### 강점

- EKS 기반 Kubernetes 운영
- Argo CD 기반 GitOps 배포
- Helm을 활용한 배포 설정 표준화
- GitLab CI 파이프라인 공통화
- Prometheus와 Alertmanager 기반 모니터링

#### 한계

- 공통 Helm Chart 변경이 여러 서비스에 영향을 줄 수 있음
- EKS 업그레이드 시 연계 도구의 호환성 검증이 필요함
- 서비스 메시와 분산 추적 구성은 공개 자료에서 확인이 제한적임
- 공통 CI/CD 구성에 문제가 발생하면 다수 서비스 배포에 영향을 줄 수 있음

## 5. 호텔 예약 서비스의 주요 페인포인트

### 5.1 특가 오픈 시 순간적인 트래픽 증가

특가 상품이나 성수기 예약이 시작되면 짧은 시간에 많은 요청이 집중될 수 있다.

평상시 트래픽을 기준으로 구성된 서버에서는 다음과 같은 문제가 발생할 수 있다.

- CPU 및 메모리 사용량 급증
- 데이터베이스 Connection Pool 고갈
- API 응답 지연과 Timeout
- 서비스 간 연쇄 장애
- 예약 요청 실패 증가

### 5.2 동시 예약으로 인한 재고 초과 판매

여러 사용자가 동일한 객실을 동시에 예약하면 각 요청이 동일한 재고 값을 조회한 뒤 재고를 차감할 수 있다.

이 경우 실제 재고보다 많은 예약이 생성되는 오버셀 문제가 발생할 수 있으므로, 재고 조회와 차감을 하나의 원자적 연산으로 처리해야 한다.

### 5.3 MSA 서비스 간 장애 전파

검색, 회원, 예약, 결제, 알림 서비스가 서로 의존하면 하나의 서비스 장애가 전체 예약 흐름에 영향을 줄 수 있다.

서비스 간 Timeout과 재시도가 반복될 경우 장애가 다른 서비스로 확대될 가능성도 있다.

### 5.4 장애 원인 분석 지연

메트릭, 로그, 트레이스가 서로 분리되어 있으면 같은 요청에서 발생한 문제를 연결하기 어렵다.

예를 들어 메트릭에서 에러율 증가를 확인한 후 관련 로그를 직접 검색하고, 다시 별도의 추적 도구에서 요청 흐름을 찾아야 한다면 원인 분석 시간이 증가한다.

### 5.5 수동 배포로 인한 환경 불일치

운영자가 직접 Kubernetes 리소스나 컨테이너 이미지를 수정하면 Git 저장소의 선언 상태와 실제 운영 환경이 달라질 수 있다.

이로 인해 현재 운영 버전 확인, 장애 재현, 변경 이력 추적, 롤백 작업이 어려워질 수 있다.

### 5.6 알림 과다와 중요 장애 식별 어려움

일시적인 지표 변화에도 알림이 발생하거나 같은 장애에 대한 중복 알림이 반복되면 운영자가 실제 중요한 장애를 놓칠 수 있다.

알림의 심각도 구분, 그룹화, 억제 및 복구 알림이 필요하다.

### 5.7 비동기 알림 처리의 추적 단절

예약 완료 후 Notice Service에서 비동기적으로 사용자 알림을 처리하면 최초 예약 요청과 알림 처리 로그가 분리될 수 있다.

비동기 이벤트에 `trace_id`가 전달되지 않으면 예약 요청부터 알림 발송까지의 전체 흐름을 추적하기 어렵다.

### 5.8 장애 대응 절차의 담당자 의존

장애 대응 절차가 문서화되어 있지 않으면 담당자마다 원인 확인 순서와 복구 방법이 달라질 수 있다.

신규 운영자나 비담당자가 장애에 대응할 경우 복구 시간이 증가하고 잘못된 조치로 장애가 확대될 수 있다.

## 7. 프로젝트 차별화 요소

### 7.1 Observability 3축 통합

Prometheus, Loki, Tempo를 Grafana와 연동하여 메트릭·로그·트레이스를 한 화면에서 확인할 수 있도록 구성하였다.

로그에는 `trace_id`와 `span_id`를 포함하여 특정 예약 요청의 로그에서 분산 추적으로 연결할 수 있도록 하였다.

### 7.2 GitOps 기반 자동 배포

GitHub Actions에서 애플리케이션 이미지를 생성하여 ECR에 저장하고, Argo CD가 Git 저장소의 변경 내용을 EKS 클러스터에 자동 반영하도록 구성하였다.

이를 통해 수동 배포로 발생할 수 있는 환경 불일치와 배포 이력 누락 문제를 줄였다.

### 7.3 특가 예약 트래픽 검증

일반적인 CRUD 테스트가 아니라 한정된 특가 재고에 다수 사용자가 동시에 접근하는 상황을 K6로 재현하였다.

다음 항목을 구분하여 측정하였다.

- 정상 구매 응답
- 재고 소진 응답
- 실제 시스템 오류
- p95 응답시간
- 재고 초과 판매 발생 여부

Redis Lua Script를 적용하여 재고 확인과 차감을 원자적으로 처리하고, 동시 요청 상황에서도 오버셀이 발생하지 않도록 구성하였다.

### 7.4 장애 감지부터 복구까지 통합 검증

본 프로젝트에서는 다음 운영 흐름을 실제로 검증하였다.

```text
서비스 장애 또는 부하 발생
        ↓
Prometheus 메트릭 변화 감지
        ↓
Alertmanager 알림 발생
        ↓
Slack 채널로 Critical 알림 전송
        ↓
Grafana에서 메트릭과 로그 확인
        ↓
Trace ID를 이용해 요청 흐름 분석
        ↓
Runbook을 참고하여 복구 수행
        ↓
Slack RESOLVED 알림 확인
```

### 7.5 Notice Service 분리

예약 완료 후 사용자 알림 기능을 별도의 `notice-service`로 분리하였다.

예약 이벤트를 비동기로 수신하여 알림을 처리하고, 다음 정보를 로그에 기록하였다.

- 예약 ID
- 사용자 이메일
- 호텔명
- 특가 상품 여부
- Trace ID
- Span ID
- 알림 처리 결과

이를 통해 알림 처리 지연이나 실패가 핵심 예약 API의 응답에 직접적인 영향을 주지 않도록 구성하였다.

## 8. 결론

Airbnb와 Agoda는 대규모 Kubernetes와 MSA 환경을 운영하며, 자동화된 배포와 Observability 체계를 통해 복잡한 서비스 구조를 관리하고 있다.

여기어때는 EKS, Argo CD, Helm, GitLab CI 등을 활용하여 배포 일관성과 운영 효율성을 높인 사례를 공개하였다. 야놀자는 국내 대표 숙박 플랫폼이지만, 공개 자료만으로는 내부 아키텍처와 Observability 구성을 상세히 확인하기 어려웠다.

호텔 예약 서비스에서는 다음 문제가 공통적으로 중요하다.

- 특가 오픈 시 순간적인 트래픽 증가
- 동시 예약에 따른 재고 정합성
- MSA 서비스 간 장애 전파
- 메트릭·로그·트레이스 분리로 인한 분석 지연
- 수동 배포에 따른 환경 불일치
- 과도한 알림과 대응 지연
- 비동기 처리 구간의 추적 단절

본 프로젝트는 이러한 문제를 해결하기 위해 다음 기술을 적용하였다.

- AWS EKS 기반 Kubernetes 환경
- 기능별 마이크로서비스 구조
- Redis Lua 기반 원자적 재고 차감
- GitHub Actions와 Argo CD 기반 GitOps
- Prometheus·Loki·Tempo 기반 Observability 통합
- Grafana 기반 상관 분석
- Alertmanager와 Slack 기반 장애 알림
- K6 기반 부하 테스트
- SLI·SLO 및 Error Budget 측정
- Runbook 기반 장애 대응 절차
- Notice Service 기반 비동기 알림 처리

따라서 본 프로젝트의 핵심 차별점은 호텔 예약 기능만 구현한 것이 아니라, **특가 트래픽과 장애 상황을 직접 재현하고 장애 감지, 원인 분석, 알림, 복구까지의 전체 운영 과정을 클라우드 네이티브 환경에서 검증했다는 점**이다.
