
# 0. 시장·서비스 비교 분석 및 클라우드 네이티브 차별화 도출
<br>

> **분석 대상:** 글로벌 여행·숙박 플랫폼 3개와 국내 여행·숙박 플랫폼 2개  
> **분석 방법:** 기업 공식 홈페이지, 기술 블로그, Kubernetes 사례, 채용 기술 스택 및 공개 발표 자료를 기반으로 분석하였다.  
> 각 기업은 전체 내부 아키텍처를 공개하지 않으므로, 공개 자료에서 직접 확인할 수 있는 내용과 합리적으로 추정한 내용을 구분하였다.

---

## 1. 분석 목적

숙박 예약 플랫폼은 일반적인 콘텐츠 서비스와 달리 다음과 같은 운영 특성을 가진다.

- 특정 시간에 특가·쿠폰·프로모션 트래픽이 집중된다.
- 하나의 객실이나 특가 재고에 여러 사용자가 동시에 접근할 수 있다.
- 검색, 가격, 재고, 예약, 결제, 알림 등 여러 서비스가 하나의 예약 요청에 연관된다.
- 외부 숙박 공급자, 결제사 및 메시징 시스템 장애가 전체 예약 흐름에 영향을 줄 수 있다.
- 예약 성공 여부와 재고 수량의 데이터 일관성이 매우 중요하다.
- 장애 발생 시 고객 결제와 예약 데이터에 직접 영향을 주기 때문에 빠른 탐지와 추적이 필요하다.

따라서 본 분석에서는 단순한 사용자 기능 비교가 아니라 다음 클라우드 네이티브 운영 항목을 중심으로 비교하였다.

1. 마이크로서비스 및 서비스 분리 구조
2. Kubernetes 기반 오케스트레이션
3. CI/CD 및 배포 자동화
4. 서비스 메시와 서비스 간 통신 관리
5. 메트릭·로그·트레이스 통합 관찰성
6. 대규모 트래픽과 선착순 이벤트 처리
7. 장애 격리, 알림 및 복구 전략

## 4. 공개 자료에서 확인된 주요 운영 페인포인트

### 페인포인트 1. 특가 오픈 시 순간적인 트래픽 폭증

숙박 플랫폼의 특가, 쿠폰 및 프로모션은 평상시보다 몇 배 이상 많은 요청을 짧은 시간에 발생시킨다. 모든 요청이 예약 서버와 데이터베이스로 직접 전달되면 Connection Pool 고갈, CPU 포화, 응답 지연 및 연쇄 장애가 발생할 수 있다.

여기어때는 대규모 선착순 쿠폰 이벤트를 위해 Redis와 Kafka를 활용한 처리 구조를 공개했으며, Airbnb도 피크 트래픽과 자동화된 Bot 요청에 대응하기 위한 Rate Limiting 및 Traffic Management 사례를 공개하였다.

**본 프로젝트의 대응**

- Redis Sorted Set 기반 대기열
- Lua Script 기반 원자적 입장 인원 승격
- Admission Token 검증
- 예약 종료 후 대기열 Slot 즉시 반환
- Kubernetes HPA 기반 수평 확장
- K6 1,000명 동시 접속 시나리오 검증

---

### 페인포인트 2. 한정된 재고의 초과 판매와 중복 예약

동일한 객실이나 특가 재고에 여러 요청이 동시에 접근하면 일반적인 조회 후 수정 방식에서는 Race Condition이 발생한다. 두 요청이 동일한 잔여 재고를 확인하면 실제 재고보다 많은 예약이 생성될 수 있다.

**본 프로젝트의 대응**

- Redis Lua Script에서 재고 확인과 차감을 하나의 원자 연산으로 수행
- 예약 서비스에서 인당 특가 구매 제한 검사
- 예약 저장 실패 시 Redis 재고를 복구하는 보상 처리
- K6 테스트에서 재고 30개에 1,000명이 동시에 구매를 시도하도록 구성
- 부하 테스트 결과 오버셀 0건 확인

---

### 페인포인트 3. 서비스 간 의존성으로 인한 연쇄 장애

예약 요청은 사용자 인증, 호텔 조회, 가격 검증, 재고 차감, 데이터베이스 저장 및 알림 발행 등 여러 서비스에 의존한다. 하위 서비스 하나의 지연이 Thread와 Connection을 점유하면 상위 서비스까지 장애가 전파될 수 있다.

여기어때 BFF 사례에서도 여러 하위 API 중 하나가 지연될 때 전체 BFF로 장애가 전파되는 Cascading Failure 위험을 설명하고 있다.

**본 프로젝트의 대응**

- `user-service`, `search-service`, `event-service`, `notice-service` 분리
- 검색 트래픽과 예약 트래픽의 장애 영역 분리
- `event-service`가 `search-service`를 호출하여 가격을 서버 측에서 재검증
- `search-service` 장애 시 잘못된 가격으로 예약을 진행하지 않고 503 반환
- Redis Streams를 이용해 예약 처리와 알림 처리를 비동기로 분리
- OpenTelemetry Trace를 이용해 서비스 호출 지연 구간 확인

---

### 페인포인트 4. 비동기 메시지의 유실·중복·순서 문제

이벤트 기반 아키텍처에서는 Producer와 Consumer의 배포, Consumer Group Rebalancing, Offset 이전 및 재처리 과정에서 메시지 중복이나 유실이 발생할 수 있다.

여기어때는 Kafka 클러스터 전환 시 메시지 데이터와 Consumer Offset 유지, 중복 소비, 메시지 누락 및 순서 변경을 주요 위험으로 제시하였다.

**본 프로젝트의 대응**

- 예약 성공 후 Redis Streams에 알림 이벤트 발행
- Consumer Group을 사용하여 알림 Consumer 관리
- 메시지에 예약 ID, 사용자 정보 및 Trace Context 포함
- 알림 서비스가 일시적으로 중단되어도 Stream에 메시지가 유지되는 구조 적용

다만 현재 구현에서는 Consumer 처리 실패 시 ACK 정책과 DLQ가 충분히 구현되어 있지 않다. 운영 수준의 신뢰성을 확보하려면 다음 개선이 추가로 필요하다.

- 처리 성공 시에만 ACK
- 최대 재시도 횟수 설정
- Pending 메시지 재처리
- 장기 실패 메시지를 별도 DLQ Stream으로 이동
- 예약 ID 기반 알림 멱등성 처리

---

### 페인포인트 5. 배포 및 설정 변경의 장애 범위 확대

대규모 서비스에서는 코드뿐 아니라 환경변수, 동적 설정, Service Mesh 설정 및 Kubernetes Manifest 변경도 장애를 발생시킬 수 있다.

Airbnb는 잘못된 설정 배포가 특정 Kubernetes Cluster의 다수 Pod를 종료시킨 사례를 공개했으며, 설정 변경 시 일부 Pod와 AZ부터 점진적으로 적용하고 이상이 감지되면 빠르게 Rollback하는 구조를 운영한다.

**본 프로젝트의 대응**

- GitHub Actions를 통한 서비스별 변경 감지
- 변경된 서비스만 Docker Image 빌드
- Amazon ECR Image Push
- Helm Values의 Image Tag 자동 갱신
- ArgoCD가 Git 상태를 기준으로 Kubernetes 배포
- `dev`와 `prod` 환경 및 브랜치 분리
- Helm을 통한 배포 설정 표준화

현재 프로젝트는 기본 Rolling Update를 사용하고 있으므로 운영 안정성을 높이려면 다음 단계로 Canary 또는 Blue/Green 배포를 도입할 수 있다.

### 페인포인트 6. 메트릭·로그·트레이스가 분리되어 원인 분석이 느려지는 문제

메트릭에서 지연 증가를 확인하더라도 관련 로그와 Trace를 별도 시스템에서 수동으로 찾아야 하면 장애 원인 분석 시간이 길어진다. 서비스가 많아질수록 요청이 어떤 서비스를 통과했는지 확인하기도 어려워진다.

Booking.com, Airbnb, NOL 및 여기어때 모두 메트릭·로그·트레이스 통합 또는 표준화의 중요성을 공개 자료에서 강조하고 있다.

**본 프로젝트의 대응**

- Prometheus: 요청량, 에러율, 지연시간 및 JVM 메트릭 수집
- Loki: 애플리케이션 구조화 로그 저장
- Tempo: 서비스 간 분산 Trace 저장
- Grafana: 세 가지 신호를 하나의 화면에서 조회
- 로그에 `trace_id` 삽입
- Grafana Derived Field를 통해 로그에서 Trace로 이동
- Tempo의 Trace에서 관련 로그로 이동
- Redis Streams 비동기 구간에 Trace Context 수동 전파
- 4 Golden Signals 기반 통합 Dashboard 구성

---

### 페인포인트 7. Observability 시스템 자체 장애와 과도한 수집 비용

Observability 데이터는 실제 비즈니스 요청보다 훨씬 많은 양이 생성될 수 있다. 모든 로그와 Trace를 무조건 저장하면 스토리지 비용과 Query 부하가 증가한다.

Airbnb는 Observability 파이프라인이 관찰 대상 Kubernetes 인프라와 동일한 시스템에 의존할 경우, 장애 시 모니터링 시스템도 함께 사용할 수 없는 순환 의존성 문제를 공개하였다. 여기어때도 트래픽 패턴과 이벤트성 피크를 고려한 Observability Right-Sizing 기준을 다루고 있다.

**본 프로젝트의 대응**

- 서비스별 Metric Scrape 주기 설정
- Loki와 Tempo 저장소를 PVC로 분리
- EBS 기반 영구 저장
- 애플리케이션별 `service.name` Label 적용
- Trace Sampling 비율을 환경변수로 조절할 수 있는 구조
- Grafana Dashboard 자동 Provisioning

현재 개발 환경에서는 Trace를 높은 비율로 수집하지만, 운영 환경에서는 다음 최적화가 필요하다.

- 정상 요청 Sampling 비율 축소
- 에러 및 고지연 Trace 우선 저장
- 로그 보존 기간 설정
- 고 Cardinality Label 제한
- 서비스별 수집량 및 비용 Dashboard 구성

### 페인포인트 8. 알림 과다와 담당자 전달 실패

단순 임계값 기반 알림을 많이 만들면 사용자 오류나 일시적인 Spike까지 Slack에 전송되어 중요한 장애 알림이 묻힐 수 있다. 반대로 야간이나 휴일에 Slack 알림만 보내면 담당자가 장애를 늦게 확인할 수 있다.

여기어때는 사용자 오류가 Slack에 과도하게 전송되어 중요한 메시지를 구분하기 어려웠던 사례와 Grafana OnCall·Amazon Connect를 활용한 전화 알림 구조를 공개하였다.

**본 프로젝트의 대응**

- HTTP 5XX 에러율 알림
- p95 Latency 알림
- Service Down 알림
- Alertmanager와 Slack Webhook 연동
- Warning과 Critical 심각도 구분
- Grafana에서 알림 발생 시 관련 메트릭과 로그 확인

추가적으로 알림 품질을 높이기 위해 다음 개선이 필요하다.

- 사용자 오류인 HTTP 4XX와 시스템 오류인 HTTP 5XX 분리
- Error Budget Burn Rate 기반 알림
- 동일 장애 알림 Grouping 및 Inhibition
- 서비스 Owner Label 추가
- Critical 알림의 전화 또는 별도 온콜 채널 연계
- 알림별 Runbook URL 연결

## 5. 프로젝트의 클라우드 네이티브 차별화 전략

본 프로젝트가 대형 상용 플랫폼보다 더 큰 규모나 더 높은 성능을 제공한다는 의미는 아니다. 본 프로젝트의 차별점은 숙박 예약 서비스에서 발생할 수 있는 핵심 운영 문제를 작은 MSA 환경에서 재현하고, 인프라·배포·관찰성·부하 테스트를 하나의 저장소에서 End-to-End로 구현했다는 것을 차별점으로 두었다.

| 구분 | 일반적인 소규모 예약 프로젝트 | 본 프로젝트 |
| --- | --- | --- |
| 서비스 구조 | 하나의 백엔드 애플리케이션 | 사용자·검색·예약·알림 서비스 분리 |
| 배포 환경 | 단일 서버 또는 Docker Compose | AWS EKS와 Kubernetes 기반 배포 |
| 환경 구축 | 수동 리소스 생성 | Terraform 기반 EKS·네트워크·ArgoCD 구축 |
| 애플리케이션 배포 | 수동 이미지 배포 | GitHub Actions + ECR + Helm + ArgoCD GitOps |
| 검색 성능 | 요청마다 DB 조회 | Caffeine Cache와 검색 조건별 조회 |
| 특가 트래픽 | 모든 요청을 예약 API로 전달 | Redis 대기열과 Admission Token으로 진입 제어 |
| 재고 관리 | DB 조회 후 재고 감소 | Redis Lua Script 기반 원자적 재고 차감 |
| 가격 검증 | 클라이언트 가격 신뢰 | `search-service`를 호출해 서버에서 가격 재계산 |
| 알림 처리 | 예약 요청 내부에서 동기 처리 | Redis Streams 기반 비동기 처리 |
| 메트릭 | CPU·메모리 중심 | 4 Golden Signals와 애플리케이션 메트릭 |

| 장애 분석 | 서버 로그 수동 탐색 | Grafana에서 Metric → Log → Trace 상관 분석 |
| 알림 | 장애 발생 후 수동 확인 | Prometheus Rule + Alertmanager + Slack |
| 성능 검증 | 단일 사용자 기능 테스트 | K6 1,000명 동시 특가 예약 시나리오 |
| 운영 목표 | 명확한 기준 없음 | Availability·Latency·Error Rate SLO 정의 |

## 6. 본 프로젝트에서 구현한 핵심 차별화 포인트

### 6.1 숙박 예약 도메인에 맞춘 트래픽 진입 제어

일반적인 HPA 기반 확장만으로는 순간적으로 유입되는 특가 트래픽을 완전히 처리하기 어렵다. 본 프로젝트는 서버를 무한히 확장하는 대신 Redis 대기열을 통해 예약 시스템에 진입할 수 있는 요청 수를 제한하였다.

이를 통해 다음 효과를 얻는다.

- 예약 서비스와 데이터베이스의 최대 동시 처리량 보호
- 사용자에게 대기 순번 제공
- 직접 API 호출을 통한 대기열 우회 차단
- 예약 완료·매진·실패 시 Slot 반환
- 후순위 사용자의 자동 승격

### 6.2 Redis 원자 연산을 통한 오버셀 방지

특가 재고 차감을 Redis Lua Script 하나에서 처리하여 조회와 수정 사이의 Race Condition을 제거하였다. 단순 분산 락보다 연산 범위가 명확하고 처리 시간이 짧으며, K6 부하 테스트에서 실제 동시 구매 상황을 검증하였다.

### 6.3 동기 호출과 비동기 이벤트를 하나의 Trace로 연결

HTTP 서비스 호출은 OpenTelemetry 자동 계측으로 연결하고, 자동 계측이 적용되지 않는 Redis Streams 구간은 Trace Context를 메시지에 직접 주입하였다.

따라서 다음 흐름을 하나의 Trace에서 확인할 수 있다.

```text
사용자 예약 요청
→ event-service
→ search-service 가격 검증
→ Redis 재고 차감
→ PostgreSQL 예약 저장
→ Redis Streams 이벤트 발행
→ notice-service 이벤트 소비
````

### 6.4 오픈소스 기반 Observability 3축 통합

상용 APM에 의존하지 않고 Prometheus, Loki, Tempo 및 Grafana를 활용하여 메트릭·로그·트레이스를 통합하였다.

이를 통해 기술 종속성을 줄이고 다음 내용을 직접 구성하였다.

* Prometheus ServiceMonitor
* Grafana Data Source Provisioning
* 4 Golden Signals Dashboard
* Loki 구조화 로그
* Tempo OTLP Trace
* 로그와 Trace 간 Derived Field
* Prometheus Alert Rule
* Alertmanager Slack 연동
* EBS PVC 기반 로그·Trace 영구 저장

### 6.5 Git 상태를 배포의 기준으로 사용하는 GitOps

GitHub Actions는 애플리케이션 이미지를 빌드하고 Helm Values의 Image Tag를 변경한다. 실제 Kubernetes 배포는 ArgoCD가 Git의 선언 상태를 기준으로 수행한다.

이를 통해 다음 효과를 얻는다.

* 누가 어떤 버전을 배포했는지 Git 이력으로 확인
* 클러스터에 직접 접속하지 않고 배포 가능
* `dev`와 `prod` 환경 분리
* 배포 상태 Drift 탐지
* 이전 Git Commit으로 Rollback 가능
* 애플리케이션별 변경 감지로 불필요한 빌드 감소

### 6.6 부하 테스트와 Observability를 연결한 검증

단순히 K6 결과만 확인하는 것이 아니라 부하 테스트 중 발생하는 요청량, 에러율, p95 지연시간, JVM Heap 및 애플리케이션 로그를 Grafana에서 동시에 관찰한다.

이를 통해 다음 과정을 수행할 수 있다.

1. K6로 특가 트래픽 발생
2. Prometheus에서 요청량과 지연 증가 확인
3. Loki에서 매진·중복 구매·예외 로그 확인
4. Tempo에서 지연이 발생한 서비스와 Span 확인
5. Alertmanager의 Slack 알림 확인
6. 원인 분석 후 설정 또는 코드 개선
7. 동일 시나리오 재실행

## 7. 해외·국내 서비스 대비 프로젝트의 위치

### 글로벌 서비스와의 차이

Booking.com, Airbnb 및 Expedia Group은 수천 개 서비스, 다중 리전, 수백 개 클러스터 및 전용 플랫폼 엔지니어링 조직을 운영한다. 본 프로젝트는 다음 항목까지는 구현하지 않았다.

* Cell 기반 장애 격리

* 전용 Internal Developer Platform
* 자동 Canary 분석
* 전사 Observability 데이터 플랫폼
* 대규모 Chaos Engineering 자동화

대신 본 프로젝트는 글로벌 서비스가 사용하는 핵심 운영 개념을 교육·검증 가능한 규모로 축소하여 구현하였다.

* Kubernetes
* GitOps
* MSA
* 비동기 이벤트

* 트래픽 대기열

### 국내 서비스와의 차이

본 프로젝트는 국내 상용 서비스 사례를 그대로 복제하기보다는 다음과 같이 하나의 시연 가능한 흐름으로 통합하였다.

```text
회원가입

→ 호텔 검색
→ 특가 대기열
→ 입장 토큰 발급
→ 가격 재검증

→ 예약 저장
```

## 8. SLO 및 신뢰성 공개 방식 비교

이번 조사 범위에서는 비교 대상 기업이 실제 고객 대상 서비스의 Availability, p95 Latency 및 Error Budget 수치를 상세하게 공개한 사례는 확인하기 어려웠다.

대신 다음과 같은 차이가 확인되었다.

| 구분          | 공개 방식                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------- |
| **글로벌 서비스** | 대규모 Kubernetes, Service Mesh, 다중 클러스터, 장애 격리, DR Test 및 Observability 플랫폼 등 운영 원칙과 내부 플랫폼 설계를 상세히 공개한다. |
| **국내 서비스**  | EKS 전환, Kafka, Redis, CI/CD, LGTM, 온콜 시스템 등 특정 문제를 해결한 실무 적용 사례를 중심으로 공개한다.                             |
| **본 프로젝트**  | 프로젝트 범위에서 측정 가능한 Availability, p95 Latency 및 Error Rate 목표를 직접 정의하고 부하 테스트와 Dashboard로 검증한다.            |

본 프로젝트에서 정의한 초기 SLO는 다음과 같다.

| SLI                     | SLO                                        |
| ----------------------- | ------------------------------------------ |
| Availability            | 최근 30일 기준 99.5% 이상                         |
| Latency                 | 특가 예약 API p95 200ms 미만                     |
| Error Rate              | Peak Time 시스템 오류율 1% 미만                    |
| Inventory Correctness   | 특가 재고 오버셀 0건                               |
| Notification Processing | 예약 알림 이벤트 유실 0건을 목표로 하되, DLQ와 재시도 정책 추가 필요 |

이 수치는 업계 전체의 표준값이 아니라 본 프로젝트에서 시스템 상태를 측정하고 개선하기 위한 초기 운영 목표이다.

## 9. 분석 결과

숙박 예약 플랫폼의 핵심 운영 문제는 단순히 서버 수를 늘리는 것으로 해결되지 않는다. 검색·가격·재고·예약·결제·알림이 분산된 구조에서는 트래픽 제어, 데이터 일관성, 장애 격리, 안전한 배포 및 통합 Observability가 함께 구축되어야 한다.

글로벌 플랫폼은 대규모 Kubernetes, Service Mesh, Cell Architecture, 다중 클러스터 및 자체 Observability 플랫폼을 통해 확장성과 장애 격리를 강화하고 있다. 국내 플랫폼은 EKS, GitOps, Kafka, Redis 및 LGTM을 실제 예약·프로모션 서비스에 적용하며 운영 표준화와 장애 대응 체계를 발전시키고 있다.

본 프로젝트는 이러한 사례에서 공통적으로 확인되는 핵심 운영 원칙을 다음과 같이 구현하였다.

1. Redis 대기열을 통한 특가 트래픽 진입 제어
2. Lua Script 기반 원자적 재고 차감과 오버셀 방지
3. 서비스별 독립 배포가 가능한 MSA
4. Redis Streams 기반 예약 알림 비동기화
5. GitHub Actions·Helm·ArgoCD 기반 GitOps
6. Prometheus·Loki·Tempo·Grafana 기반 Observability 3축 통합
7. Trace ID를 통한 Metric·Log·Trace 상관 분석
8. Alertmanager와 Slack을 통한 장애 알림
9. K6 1,000명 동시 접속 기반 성능 및 안정성 검증
10. Availability·Latency·Error Rate 기반 SLO 정의

따라서 본 프로젝트의 차별화 지점은 단순한 호텔 예약 기능 구현이 아니라, **특가 트래픽이 발생하는 숙박 예약 서비스를 대상으로 배포·관찰성·동시성 제어·장애 대응을 하나의 클라우드 네이티브 운영 흐름으로 통합하고 실제 부하 테스트로 검증했다는 점**이다.
